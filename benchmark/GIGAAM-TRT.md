# GigaAM через TensorRT

Отдельный Compose-проект `speech-comparison-gigaam-trt`. Два режима:

- урезанный, по умолчанию: поиск речи → распознавание → паузы;
- полный, флаг `--full`: то же и голоса собеседников с эмоциями — [раздел ниже](#полный-flow-голоса-и-эмоции).

Языковая модель не запускается ни в одном.

Из папки `temptest`:

```bash
BENCH_GPU=0 \
BENCH_GPU_MIN_FREE_MIB=12288 \
BENCH_GPU_MAX_UTIL=100 \
BENCH_GPU_RESERVE_MIB=3072 \
bash benchmark/run-gigaam-trt.sh ../audio
```

Обрабатываются все записи папки, включая подпапки, подряд и без пауз; число записей не ограничено.
Запись длиннее 30 минут останавливает прогон ещё на подготовке; предел меняет `--max-audio-seconds`.

## Несколько записей одновременно

`--parallel N` обрабатывает N записей сразу, по умолчанию одну. Скрипт сам выделяет по два ядра
на поток (набор ядер `0…2N−1`), память клиенту и одну копию энкодера в Triton на каждые пять потоков.
Свои значения задают `BENCH_CLIENT_CPUS`, `BENCH_CPUSET`, `BENCH_CLIENT_MEMORY`, `BENCH_TRITON_INSTANCES`.

При нескольких потоках время одной записи измеряется под нагрузкой соседей, а счётчики Triton
общие для всех записей и с клиентом на каждой записи не сверяются. Общая скорость всех потоков —
`итоги.json → systems.gigaam_trt.wall`: записей за 15 минут и отношение к реальному времени по часам,
вместе с запуском клиента и прогревом перед каждой записью. Там же время ожидания в очереди Triton.

`--reference-run benchmark-results/<прогон>` сверяет имена файлов, SHA256 моно PCM и запись
прогрева с прежним прогоном. Логи видны в терминале и пишутся в папку прогона. Отключение SSH
прерывает запуск; для долгого прогона используйте `tmux`.

## Полный flow: голоса и эмоции

```bash
bash benchmark/run-gigaam-trt.sh ../audio --full
```

Распознавание то же, что в урезанном режиме. Поверх него работает исходная сессия монитора
(`app/session.py`) без языковой модели:

| Часть | Где считается |
|---|---|
| Голоса собеседников, CAM++ | CPU, два потока; `BENCH_SPEAKER_PROVIDER=cuda` переносит на GPU |
| Эмоции, GigaAM-Emo, fp16 | GPU, PyTorch в процессе обработчика |

Во фрагменте речи от 3,2 с окна по 1,5 с с шагом 0,5 с ищут смену говорящего; затем считается
вектор голоса каждой реплики. Эмоции определяются по первым 12 с реплики длиной от 0,5 с и идут
одновременно с распознаванием. Подсказка «кто говорит сейчас» отключена: она нужна живому
микрофону и на реплики не влияет.

Голоса стоят на CPU по той же причине, что поиск речи: модель маленькая, вызовов много.
Замер на RTX 4070 SUPER: окно 1,5 с — 28 мс на CPU в один поток против 70 мс на GPU.

Модель эмоций своя у каждого потока: около 1 ГиБ видеопамяти и 3 ГиБ памяти на обработчик.
До запуска скрипт проверяет свободную видеопамять: резерв + 2048 МиБ серверу моделей + 1536 МиБ
на поток (`BENCH_EMOTION_VRAM_MIB`). Веса `emo.ckpt` лежат в `benchmark-cache/gigaam`; подготовка
проверяет их и скачивает, если их нет.

Результаты пишутся в `benchmark-results/gigaam-trt-full-ДАТА-ВРЕМЯ-PID/` под ключом
`gigaam_trt_full`. К файлам записи добавляется `gigaam_trt_full-диалог.txt` — реплики с
собеседником и эмоцией; `gigaam_trt_full.txt` остаётся обычным текстом. В `замеры.csv` появляются
колонки голосов, эмоций и числа собеседников. Времени каждого слова в репликах полного режима нет:
исходная сессия его не хранит.

Загрузка модели эмоций добавляет несколько секунд к запуску обработчика каждой записи. В замер
они не входят, но прогон по часам заметно дольше урезанного.

## Как устроено

| Часть | Где считается |
|---|---|
| Поиск речи Silero VAD, порции по 100 мс | CPU; `BENCH_VAD_PROVIDER=cuda` переносит на GPU |
| Звуковые признаки | CPU |
| Энкодер GigaAM `v3_e2e_rnnt`, fp16 | GPU, TensorRT в Triton |
| Жадный декодер RNN-T | CPU, ONNX Runtime |

Поиск речи стоит на CPU намеренно. Модель крошечная и вызывается около 2000 раз на запись;
на GPU каждое обращение дороже самого расчёта. Замер на одной записи длиной 199 с на
RTX 4070 SUPER: 0,6 с на CPU против 6,4 с на GPU, границы фрагментов одинаковые.

Каждый найденный фрагмент речи — один запрос к энкодеру. Движок принимает фрагменты от 0,16
до 32 с; детектор режет речь не длиннее 15 с.

## Подготовка

Всё это вне замеров:

1. Проверяется образ `nvcr.io/nvidia/tritonserver:25.06-py3`. Если реестр отвечает 403, образ
   загружается через прокси: `python3 benchmark/fetch_triton_image.py --load`
   (подробности — [TONE-TRT.md](TONE-TRT.md)).
2. Собирается клиентский образ — тот же Dockerfile, что у клиента T-one, поверх общего
   образа библиотек. Если общего образа нет, он собирается через `compose.trt-base.yml`.
3. Контейнер без GPU и аудио загружает веса GigaAM и экспортирует энкодер, декодер и joint
   в ONNX. Веса берутся из `benchmark-cache/gigaam`; сеть нужна, только если их там нет.
4. Контейнер без сети и аудио собирает TensorRT-движок энкодера на выбранной GPU. При тех же
   весах, GPU, драйвере и версии TensorRT движок используется повторно.
5. Поднимается собственный Triton и ждётся готовность модели.

Вместе с ONNX сохраняется состояние экстрактора признаков. Окно и мел-фильтры лежат в весах
обученной модели и отличаются от создаваемых заново; без них текст расходится с PyTorch
примерно в четверти фрагментов.

## Что измеряется

Для каждой записи — отдельный клиентский процесс; его загрузка и 30-секундный прогрев вне
замеров. Энкодер постоянно находится в Triton. В замер входят поиск речи, признаки, обмен
с Triton, энкодер и декодер.

`elapsed_seconds` — вся обработка записи. `asr_seconds` — сумма вызовов распознавания; она
идёт одновременно с поиском речи. `trt_stages` делит распознавание на признаки, энкодер
с gRPC и декодер. Статистика Triton до и после записи лежит рядом.

Сверка с прежним режимом через PyTorch на 100 записях (12.10.2026, RTX 4070 SUPER): время
обработки 64 с против 662 с; из 19 957 слов отличаются 23, в 14 записях. Режим через PyTorch
из стенда убран; его сохранённый прогон можно передать в `--reference-run`.

## Файлы

- `benchmark-cache/gigaam-trt/` — ONNX-части, движок и их метаданные;
- `benchmark-results/gigaam-trt-ДАТА-ВРЕМЯ-PID/` — результаты запуска; у полного режима — `gigaam-trt-full-…`;
- `условия.json`, `итоги.json`, `замеры.csv`, `отчёт.html`, `отчёт.md`;
- `записи/0001/gigaam_trt.*` — текст, реплики со временем слов, паузы, подготовка и прогрев;
- `логи/запуск.log`, `экспорт.log`, `сборка-tensorrt.log`, `triton.log`, `gigaam-trt.log`, `gpu.csv`;
- `диагностика.tar.gz` — архив без аудио и моделей, с текстами разговоров.

Контейнеры обработки общаются по внутренней сети; порты не публикуются. При выходе
останавливаются только контейнеры этого запуска; автоматического удаления нет.
Полный успех: состояние `Завершён`, код запуска 0 и результат у каждой записи.
