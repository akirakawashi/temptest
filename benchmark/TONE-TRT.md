# Новый тест T-one через TensorRT

Отдельный Compose-проект `speech-comparison-tone-trt`. Исходный тест
`run-tone.sh` остаётся доступным. Новый прогон не меняет прежние результаты.

Из папки `temptest`:

```bash
BENCH_GPU=0 \
BENCH_GPU_MIN_FREE_MIB=12288 \
BENCH_GPU_MAX_UTIL=100 \
BENCH_GPU_RESERVE_MIB=3072 \
bash benchmark/run-tone-trt.sh ../audio \
  --reference-run benchmark-results/20261008-163940-3995135
```

`--reference-run` сверяет имена всех 100 файлов, SHA256 моно PCM и запись
прогрева со старым тестом. Исходная папка подключается только для чтения.
Если она уже удалена с сервера, параметр можно убрать: файлы всё равно
получат собственные SHA256, но автоматической сверки с прошлым корпусом не будет.

Сначала обрабатываются все 100 записей без KenLM, затем те же 100 с KenLM.
Для запуска только первого режима добавьте `--without-kenlm` — языковая
модель тогда даже не скачивается. Это другой режим качества, а не замена
полного теста с KenLM.

Логи сразу видны в терминале и одновременно пишутся в папку прогона.
Отключение SSH прерывает foreground-запуск. Если нужно отключаться,
запускайте команду в заранее открытой сессии `tmux`; без неё дождитесь окончания.

## Подготовка

1. Проверяется наличие официального образа `nvcr.io/nvidia/tritonserver:25.06-py3`.
   Если он уже есть локально, обращения к реестру нет. Иначе он скачивается;
   при ошибке подготовка останавливается до сборки клиента и запуска моделей.
2. Собирается новый клиентский образ: официальный Python-пакет T-one,
   KenLM и gRPC-клиент. KenLM компилируется в отдельном Docker-слое; apt
   и установка пакетов в Python сервера не используются.
3. Контейнер без GPU и без аудио скачивает закреплённую ONNX-модель
   (144 МБ) и KenLM (5,46 ГБ), проверяет размер и SHA256.
4. Контейнер без сети и аудио собирает TensorRT-движок на выбранной GPU.
   Версия TensorRT, модель, GPU UUID, драйвер, команда и SHA256 движка
   сохраняются. При совпадении условий движок повторно используется.
5. Поднимается собственный Triton и ждётся готовность модели.

Это всё вне замеров. TensorRT использует batch=1; увеличение размера
батча и параллельная обработка звонков здесь не тестируются. Workspace
сборки — 1024 МиБ (`BENCH_TRT_WORKSPACE_MIB`, 128–4096); это ограничение
workspace, а не всей памяти GPU. Время сборки ограничено часом
(`BENCH_TRT_COMPILE_TIMEOUT`).

## Если nvcr.io отвечает 403 Forbidden

Клиентский образ может успешно собраться, а скачивание Triton получить
`403 Forbidden`. Это отказ в доступе к реестру; по одному этому коду нельзя
определить, связан ли он с авторизацией, политикой реестра или сетевым посредником.
До получения образа записи не обрабатываются. Изменение Python-зависимостей
или порогов памяти GPU этот отказ не исправляет.

Можно восстановить разрешённый доступ к реестру на сервере либо перенести
тот же официальный образ с машины, у которой такой доступ есть. На ней:

```bash
docker pull --platform=linux/amd64 nvcr.io/nvidia/tritonserver:25.06-py3
docker image save -o triton-25.06-py3.tar nvcr.io/nvidia/tritonserver:25.06-py3
sha256sum triton-25.06-py3.tar > triton-25.06-py3.tar.sha256
```

Передайте оба файла на сервер и в папке с ними выполните:

```bash
sha256sum -c triton-25.06-py3.tar.sha256
docker image load -i triton-25.06-py3.tar
docker image inspect --format '{{.Os}}/{{.Architecture}} {{.Id}}' \
  nvcr.io/nvidia/tritonserver:25.06-py3
```

Проверка должна вывести `linux/amd64`. Перенос не требует GPU на исходной
машине, не запускает контейнеры и не ставит пакеты в систему сервера.
Нужен свободный диск для Docker-образа и архива. Это перенос именно образа;
записи разговоров в него не входят. Команды сохранения и загрузки описаны
в [документации Docker](https://docs.docker.com/reference/cli/docker/image/save/).

После загрузки снова запустите обычную команду прогона. Используется
локальный образ; контейнеры запускаются с `--pull never`. Новая папка
результатов создаётся автоматически; прежние результаты и кеш сохраняются.
Автоматическая замена на сторонний образ или другую версию Triton отсутствует.

## Что именно измеряется

Для каждой записи — отдельный клиентский процесс, загрузка декодера и
30-секундный прогрев вне замеров. Акустическая модель постоянно находится
в нашем Triton; повторная загрузка серверной модели не имитируется.
Во время распознавания контекст сохраняется на протяжении всего файла.
Используется официальный `StreamingCTCPipeline`, а внешний Silero VAD
не вырезает тишину и не разбивает запись на независимые потоки.

Общий вход совпадает с прежним тестом: моно PCM16 16 кГц. В замер входят:

- фильтрация и пересчёт частоты до 8 кГц;
- чанки по 300 мс, передача аудио и состояния в Triton, акустика TensorRT;
- официальный logprob splitter и финализация последней фразы;
- greedy-декодер либо официальный KenLM beam search (beam=200,
  alpha=0,4, beta=0,9), оба на CPU.

`elapsed_seconds` и `asr_seconds` — весь этот цикл. Отдельно сохраняются
`acoustic_rpc_seconds` и `trt_stages`: акустика с gRPC, границы фраз,
декодер, пересчёт частоты. Клиентские времена gRPC не выдаются за чистое
время вычисления GPU; статистика Triton до и после записи лежит рядом.
Доля времени каждого этапа рассчитывается без двойного счёта.

Официальная модель strongly typed: сигнал INT32, состояние FP16,
выход logprobs FP32. CPU-декодер KenLM — часть алгоритма распознавания,
он не является GigaChat и не оценивает разговор. Голоса, эмоции и LLM
не вызываются. Паузы оценены официальным splitter; они отличаются от
Silero VAD. Есть тайминги фраз; пословные метки не выдумываются.

## Файлы и остановка

- `benchmark-cache/tone-trt/` — два исходных файла, движок и его метаданные;
- `benchmark-results/tone-trt-ДАТА-ВРЕМЯ-PID/` — результаты этого запуска;
- `условия.json`, `итоги.json`, `замеры.csv`, `отчёт.html`, `отчёт.md`;
- `записи/0001/tone_trt_greedy.*`, `tone_trt_kenlm.*` — исходные тексты,
  фразы, каждый измеренный вызов, прогрев, ошибки и подготовка;
- `логи/запуск.log`, `загрузка.log`, `сборка-tensorrt.log`, `triton.log`,
  `t-one-trt.log`, `gpu.csv`, `образы.json` — полная диагностика;
- `диагностика.tar.gz` — архив без аудио и моделей, с текстами разговоров.

Контейнеры обработки общаются по внутренней сети; порты на сервере не
публикуются. Загрузчик имеет сеть, но не получает аудио. Docker socket
контейнерам не подключается. Общий замок исключает одновременные наши тесты.
GPU общая с продом: память и нагрузка проверяются, резерв контролируется
каждые 2 секунды, но изоляции производительности общей GPU нет.

При выходе останавливаются только точные ID контейнеров, созданных этим
запуском, с проверкой метки проекта. Автоматическое удаление контейнеров,
сетей, образов и кеша отключено. Временные WAV и незаконченные файлы
подготовки удаляются внутри папок этого стенда. Работающие продовые
контейнеры не останавливаются и не перезапускаются.

Полный успех: состояние `Завершён`, код запуска 0 и 100 завершённых
результатов в каждом из двух режимов. Старые времена автоматически не
переносятся: отдельный прогон имеет другую дату и фоновую нагрузку.
Точность требует прослушивания и контрольной расшифровки.

Основа: [официальный TensorRT/Triton](https://github.com/voicekit-team/T-one/blob/main/docs/triton_inference_server.md).
